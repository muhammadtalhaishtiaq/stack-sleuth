The Problem

A test breaks. You know it's somewhere in the last 50 commits, but which one? Manual bisecting eats an hour. StackSleuth automates the entire debugging loop: reproduce the failure, bisect to the culprit commit, propose a fix, and verify, all behind a human approval gate.

Live Demo

Below is a real run against a demo pricing library. Eight commits. One of them broke the bulk discount. Watch StackSleuth find it.

$ sleuth run-tests
Running pytest...
FAILED test_bulk_discount_tier - assert 100.0 == 90.0
9 passed, 1 failed

$ sleuth reproduce test_bulk_discount_tier --runs 3
Run 1: FAILED | Run 2: FAILED | Run 3: FAILED
Deterministic failure confirmed (3/3)

$ sleuth bisect
Bisecting: 8 commits, checking...
afcc8ee^ (good) → 3e67ebe (bad) → afcc8ee (bad)
Culprit: afcc8ee "refactor: simplify discount tier lookup"

$ sleuth inspect afcc8ee
- if qty >= 10:
+ if qty > 10:
Off-by-one: boundary qty=10 no longer gets the discount

$ sleuth propose-patch
Proposal saved. Status: proposed (NOT applied)
Waiting for human approval...

$ # Human reviews the diff, approves
$ sleuth apply-patch --approved
Patch applied. Running verification...
10 passed ✓

How It Works

Reproduce

Runs the failing test 3 times in isolation to confirm it's deterministic, not flaky.

Bisect

Automates git bisect across the commit range. Found the culprit in 2 steps.

Propose

Reads the culprit diff, explains the root cause, and drafts a minimal fix.

Human Gate

Patches are never applied without explicit approval. You stay in control.

Verify

After approval, applies the patch and re-runs the full suite. 10/10 green.

Evidence Log

Every step is logged with timestamps. Full audit trail of the debugging session.

Built for IBM Bob

StackSleuth runs as an MCP server inside IBM Bob IDE. Six tools: run_tests, reproduce, bisect, inspect_commit, propose_patch, apply_patch. Every tool shells out to real pytest and git. Nothing simulated.
